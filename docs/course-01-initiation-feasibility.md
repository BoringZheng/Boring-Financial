## 2. 项目背景

Boring Financial 是一个面向个人记账和消费分析场景的智能账单分类系统。项目目标是通过“大模型语义初分 + 人工校正”的方式，解决传统记账软件自动分类不透明、语义误判后难以修正的问题。

个人用户在使用自动记账或整理微信、支付宝账单时，通常会遇到三类问题：

1. 自动分类只根据商户名或关键词判断，容易忽略真实消费语义。
2. 分类依据不透明，用户不知道为什么一笔交易被归到某个类别。
3. 语义误判会污染后续统计，用户需要可控的人工校正入口。

例如，用户向东南大学饭卡充值时，账单商户可能显示为“东南大学”。传统关键词分类容易将其归为“学习”，但从消费意图看它更接近“餐饮/校园卡充值”。因此，本项目围绕“导入 -> 大模型初分 -> 人工校正 -> 分析 -> 报表”的闭环展开，帮助用户把原始账单转换为语义更准确、可解释、可修正的财务分析结果。

## 3. 项目目标

| 目标 | 说明 |
|---|---|
| 完成记账分析闭环 | 支持账单导入、解析、大模型初分、人工校正、统计分析、消费人格画像、家庭组织聚合和 PDF 报表 |
| 支持多用户、家庭组织与数据隔离 | 用户默认只能访问自己的账单、交易、分类和报表；加入家庭组织后可按成员权限查看聚合数据 |
| 支持语义分类与人工校正 | 以大模型语义分类为主，同时保留规则兜底和人工修正入口 |
| 支持工程化部署 | 提供清晰的架构、接口、开发、部署和测试材料 |
| 控制实现复杂度 | 聚焦记账分析闭环，不引入支付、清算和银行级风控 |

## 6. 项目范围

### 6.1 范围内功能

| 模块 | 范围 |
|---|---|
| 用户认证 | 注册、登录、JWT 鉴权、多用户数据隔离 |
| 账单导入 | 支持微信/支付宝账单文件导入、批次状态和导入记录 |
| 账单解析 | 将不同平台账单转换为统一交易结构 |
| 大模型初分 | 支持模型语义分类、分类理由、分类缓存和重试队列 |
| 人工校正 | 用户可以复核低置信度交易并修正分类 |
| 分类管理 | 支持系统分类和用户自定义分类 |
| 财务看板 | 展示收入、支出、结余、储蓄率、分类占比和 Top 商户 |
| 消费人格 | 基于交易数据生成 16 型消费人格画像、财务健康评分和问卷自评对比 |
| 家庭组织 | 支持创建家庭组织、管理成员角色，并聚合家庭 Dashboard、家庭消费人格和家庭报表 |
| PDF 报表 | 按日期和导入文件生成可下载报表 |
| 部署 | 支持本地开发、Docker Compose 和裸机部署说明 |

### 6.2 范围外功能

| 不做内容 | 原因 |
|---|---|
| 支付、转账、清算 | 涉及真实资金流，超出项目范围 |
| 银行级风控 | 需要合规、审计和高安全保障，不属于记账分析闭环 |
| 多机构财务管理 | 当前定位为个人账单分类和分析 |
| 复杂家庭预算审批 | 当前家庭组织只做成员聚合、角色管理和分析，不做预算审批流 |
| 商业化运营后台 | 当前系统聚焦个人使用和轻量部署，不覆盖商业运营能力 |

## 7. 可行性分析

| 维度 | 结论 | 依据 |
|---|---|---|
| 业务可行性 | 可行 | 自动记账分类误判会影响统计质量，大模型初分、人工校正、消费人格分析和家庭聚合价值明确 |
| 技术可行性 | 可行 | 技术栈成熟，FastAPI、Vue、SQLAlchemy、Docker 和模型接口均适合轻量生产化原型 |
| 进度可行性 | 可行 | 项目周期覆盖 3 月到 6 月，4 人可以按前端、后端、模型、测试并行推进 |
| 资源可行性 | 可行 | 本地电脑即可开发联调，Git、Docker、PostgreSQL、Redis 和可选模型 API 均可获得 |
| 经济可行性 | 可行 | 项目预算低，主要成本为成员时间和可选模型调用费用 |
| 维护可行性 | 基本可行 | 采用 monorepo、分层后端、前端组件化和文档化部署，便于后续维护 |

## 9. 风险矩阵

| 风险 | 概率 | 影响 | 风险等级 | 缓解措施 |
|---|---:|---:|---:|---|
| 微信/支付宝账单格式差异 | 高 | 中 | 高 | 使用 ParserRegistry 和统一交易结构，保留测试样例 |
| 大模型分类结果不稳定 | 中 | 中 | 中 | 展示分类理由，保留规则兜底、分类缓存和人工校正 |
| 外部模型 API 不可用或延迟高 | 中 | 中 | 中 | 支持本地模型服务和 retry_queue，可切回规则/本地 mock |
| 家庭组织权限配置错误 | 中 | 高 | 高 | 使用 OrganizationMember 角色校验，个人模式默认不受组织功能影响 |
| 后期时间不足 | 中 | 高 | 高 | 先完成 MVP 闭环，再补增强功能和文档 |
| 多人协作接口不一致 | 中 | 中 | 中 | 使用 API 文档、类型定义和后端测试控制接口变化 |
| 安全设计不足 | 中 | 高 | 高 | 使用 JWT、密码哈希、多用户隔离，并在后续安全章节列出改进项 |
| 大文件导入性能不足 | 中 | 中 | 中 | 当前限制上传规模，后续通过异步任务、批量写入和 SQL 聚合优化 |

## 10. 替代方案与选择理由

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 仅使用关键词规则分类 | 稳定、可控、实现简单 | 难以理解“东南大学饭卡充值”等语义场景，误判后统计失真 | 不作为主要方案 |
| 仅使用大模型自动分类 | 语义理解能力强 | 用户缺少最终控制权，模型错误会直接污染统计 | 不作为完整方案 |
| 大模型初分 + 人工校正系统 | 兼顾语义理解、可解释性和用户控制权 | 实现复杂度更高 | 作为最终方案 |

最终选择“大模型初分 + 人工校正”的前后端分离系统，并保留规则兜底和重试机制。该方案既能提升自动分类的语义准确性，又能让用户在关键错误上保留最终控制权。

## 11. 决策者视角结论

从项目决策者视角看，Boring Financial 的收益明确、范围可控、技术栈成熟、团队分工清晰。项目不处理真实资金流，降低了安全和合规风险；同时保留本地模型、规则兜底和人工校正，降低外部模型不可用或分类误判带来的交付风险。因此，本项目适合继续推进为一个轻量、可部署、可维护的个人记账分析系统。
