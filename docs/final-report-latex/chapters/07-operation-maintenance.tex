\chapter{运行与维护}

本章阐述系统的运行环境配置、性能管理策略、可靠性保障机制以及日常运维检查要点。

\section{运行环境}

系统的运行时组件栈自上而下由以下部分构成：

\begin{description}
  \item[浏览器端] 用户通过现代浏览器（Chrome/Firefox/Edge/Safari 最新两个主要版本）访问 Vue 3 构建的单页应用。前端仅需静态文件托管，无服务端渲染（SSR）需求。
  \item[Nginx] 生产环境反向代理与静态文件服务。静态资源（HTML/CSS/JS/字体/图片）由 Nginx 直接返回，API 请求通过 \texttt{proxy\_pass} 转发至后端 Uvicorn 进程。建议配置 gzip 压缩（\texttt{application/javascript}、\texttt{text/css}）、合理的缓存头（静态资源 \texttt{Cache-Control: max-age=31536000}，含 hash 的文件名天然支持缓存失效）以及 HTTPS 终端（通过 Let's Encrypt 等证书）。
  \item[FastAPI / Uvicorn] 后端应用进程，监听 \texttt{127.0.0.1:8000}（不直接暴露于公网）。Uvicorn 的 worker 数量根据 CPU 核心数设置（建议 \texttt{workers = CPU\_CORES * 2 + 1}），生产环境可通过 systemd 或 Docker 管理进程生命周期。
  \item[PostgreSQL / SQLite] 主数据库。生产环境推荐 PostgreSQL 14+，轻量部署或开发环境可使用 SQLite（文件级数据库，无需独立进程）。
  \item[Redis] Celery 消息代理与结果后端。轻量部署模式下（\texttt{TASK\_ALWAYS\_EAGER = true}）可省略。
  \item[Retry Queue Worker] 后台线程，随 FastAPI 应用进程生命周期管理。负责按 \texttt{updated\_at} 顺序串行消费待重试的外部模型分类请求。
  \item[Local Model Service / vLLM] 可选的本地大模型推理服务，通过 OpenAI-compatible API 接口提供服务，推荐部署于独立 GPU 服务器或同一主机的独立进程中。
  \item[OpenAI-compatible API] 外部大模型服务，通过 HTTPS 调用。支持任何兼容 OpenAI Chat Completions 接口的服务（如 DeepSeek、通义千问、Moonshot 等）。
\end{description}

文件存储方面，用户上传的账单原始文件存放于 \texttt{uploads/} 目录（按用户 ID 创建子目录），生成的 PDF 报表存放于 \texttt{reports/} 目录。建议定期清理超过 90 天的上传文件以控制磁盘占用。

\section{可靠性保障}

系统通过以下五项机制保障数据处理的可靠性：

\begin{enumerate}
  \item \textbf{去重哈希（dedupe\_hash）}。每笔交易入库前，由 \texttt{TransactionNormalizer} 对平台、时间、金额（保留两位小数）、商户（NFKC 归一化后）、商品（NFKC 归一化后）五个字段拼接后计算 SHA-256 哈希。\texttt{transactions} 表的 \texttt{(user\_id, dedupe\_hash)} 联合唯一约束在数据库层面阻止重复插入。同一文件多次导入时，重复交易自动跳过，避免数据膨胀。
  \item \textbf{统一重试池}。外部大模型 API 调用不直接由业务请求线程执行。\texttt{CompositeClassifier} 将需外部分类的交易标记为 \texttt{auto\_provider = "retry\_queue"} 后立即返回，由后台 \texttt{RetryQueueWorker} 线程按 \texttt{updated\_at} 升序串行取出一条交易调用外部 API。重试采用指数退避策略：每次超时后 \texttt{api\_retry\_count} 递增，等待间隔按 $\text{base\_delay} \times 2^{\text{retry\_count}}$ 增长（上限 300 秒）。达到 \texttt{RETRY\_QUEUE\_MAX\_RETRIES} 上限后，交易标记为 \texttt{retry\_failed} 并从活跃队列中移除，不混入人工校正列表（避免用户在 Review 页面看到非自身错误导致的异常交易）。管理员可通过 \texttt{POST /api/classification/retry-all} 将失败交易重新入池。
  \item \textbf{导入批次状态机}。批次状态按 \texttt{queued \(\rightarrow\) processing \(\rightarrow\) done/partial\_failed/failed} 流转。\texttt{progress\_percent} 属性根据 \texttt{processed\_count / total\_count} 动态计算。前端轮询 \texttt{GET /api/imports} 获取批次列表，实时展示导入进度条与状态标签。\texttt{partial\_failed} 状态表示部分交易处理失败但整体流程可继续。
  \item \textbf{报表任务状态机}。与导入批次类似，\texttt{ReportJob} 状态按 \texttt{queued \(\rightarrow\) processing \(\rightarrow\) done/failed} 流转。异步生成模式（Celery Worker）确保大报表生成不阻塞 API 线程，用户可在生成完成后下载。
  \item \textbf{接口级权限校验}。所有业务接口在执行查询前均通过 \texttt{get\_current\_user} 依赖注入验证身份，并在查询中添加 \texttt{user\_id} 或组织成员身份过滤。资源归属检查覆盖交易查询、分类修正、批次删除、报表下载等所有变更操作。跨用户或非组织成员的访问尝试统一返回 403 Forbidden。
\end{enumerate}

此外，建议在生产服务器上配置以下监控：

\begin{itemize}
  \item \textbf{进程存活监控}：通过 systemd 的 \texttt{Restart=always} 或 Docker 的 \texttt{restart: unless-stopped} 确保 Uvicorn 和 Nginx 进程异常退出后自动重启。
  \item \textbf{内存与 CPU 监控}：使用 \texttt{htop} 或 Prometheus + Node Exporter 监控服务器资源消耗，关注内存泄漏与 CPU 尖刺。
  \item \textbf{磁盘 I/O 监控}：SQLite 在写入密集型场景下可能出现锁竞争，若切换至 PostgreSQL 则可显著缓解。
  \item \textbf{外部 API 可用性告警}：若 Retry Queue 的失败数量持续超过阈值，应触发告警通知运维人员检查外部模型服务的可用性与配额状态。
\end{itemize}
