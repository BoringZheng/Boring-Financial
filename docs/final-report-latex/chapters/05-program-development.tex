\chapter{程序开发}

本章阐述系统的程序组织方式、数据库设计、设计模式应用以及核心流程设计。面向对象设计集中体现在四个子系统：领域实体模型、分类器策略链、账单解析器注册表与报表构建器。

\section{面向对象程序组织}

系统并非全量采用面向对象范式——在用户认证、API 路由、Dashboard 聚合等模块中，函数式与过程式组织更为自然。OO 原则集中于以下四个区域。Pydantic DTO 与 FastAPI 依赖注入在前一章安全机制部分已做阐述。

\subsection{领域实体及其关联关系}

系统使用 SQLAlchemy ORM 定义 12 个实体，统一继承 \texttt{Base(DeclarativeBase)}，采用 Data Mapper 模式将领域模型与持久化逻辑解耦——实体类不包含 SQL 语句，所有查询通过 Session 与 Select 构建器完成。

\texttt{TimestampMixin}（\texttt{models/entities.py:12}）通过 Python 多重继承为 8 个实体提供 \texttt{created\_at/updated\_at} 字段，以 Mixin 模式横向复用时间戳关注点，消除字段声明重复。

实体关联的核心拓扑如下：\texttt{User} 位于关联中心，向多个方向辐射——通过 \texttt{import\_batches} 管理导入任务，通过 \texttt{transactions} 持有全部交易记录，通过 \texttt{categories} 维护自定义分类；\texttt{ImportBatch} 聚合 \texttt{UploadedFile}，两者共同关联至 \texttt{Transaction}；\texttt{Transaction} 通过 \texttt{auto\_category\_id} 与 \texttt{final\_category\_id} 双 FK 指向 \texttt{Category}，同时向 \texttt{ClassificationResult} 和 \texttt{ClassificationCache} 辐射分类历史与缓存；家庭组织域中 \texttt{Organization} 通过 \texttt{OrganizationMember} 关联表与 \texttt{User} 建立多对多关系。

\texttt{Transaction} 表基于 \texttt{(user\_id, dedupe\_hash)} 唯一约束实现去重，\texttt{dedupe\_hash} 由时间、金额、商户、商品、备注五字段的规范化值经 SHA-256 生成。双分类字段设计中 \texttt{auto\_category\_id} 存储模型/规则的建议分类（可被重分类更新），\texttt{final\_category\_id} 存储人工修正后的最终分类，非 NULL 时优先于自动分类。\texttt{ClassificationResult} 表只增不改，每次分类操作新增一条记录，用于追溯分类器表现变化。

\subsection{分类器策略}

分类子系统围绕策略、责任链与外观三种模式组织，由五个类构成。

\texttt{CompositeClassifier}（\texttt{services/classifiers.py:267}）作为外观入口封装分类全流程。其 \texttt{classify()} 方法编排三级责任链：检查 \texttt{ClassificationCache} 缓存 → 调用模型 API（外部模型或本地模型，由配置决定）→ \texttt{RuleBasedClassifier} 规则兜底。外部模型请求通过重试队列异步入队，避免并发 API 调用；超时异常经指数退避重试，达到上限后标记为 \texttt{retry\_failed} 并从活跃队列移除。\texttt{OpenAICompatibleClassifier} 与 \texttt{LocalModelClassifier} 均实现统一的 \texttt{classify(transaction) -> ClassificationOutput} 调用约定——前者通过 httpx 调用 OpenAI-compatible \texttt{/chat/completions}，后者继承前者并覆盖 provider 配置指向本地 vLLM 服务，两者作为同一层级的可替换策略。\texttt{RuleBasedClassifier} 按优先级匹配分类规则，命中返回置信度 0.99，未命中返回 None。\texttt{ClassificationOutput} 作为 dataclass 统一承载分类结果。

Strategy 模式使三种分类器可互换，各自封装不同的分类逻辑。Chain of Responsibility 提供优雅降级路径——缓存命中直接返回，模型不可用时自动降至规则。Facade 模式将缓存管理、重试逻辑、结果存储等复杂性隐藏在 \texttt{classify()} 内部，调用方只需传入交易对象。

\subsection{账单解析器}

解析子系统负责将微信/支付宝异构账单文件转换为统一交易结构，采用策略、适配器与注册表三种模式。

\texttt{ParserRegistry}（\texttt{services/parsers.py:239}）作为工厂入口，\texttt{parse\_file(path)} 方法执行完整流程：通过文件名关键字与文件内容预览检测平台 → \texttt{StatementReader} 读取文件（自动检测 6 种编码、定位表头行、适配 Excel/CSV 格式）→ 选择对应平台解析器 → 转换为 \texttt{ParsedTransaction} 统一结构 → \texttt{TransactionNormalizer} 对商户、商品、备注字段做 NFKC 归一化并生成 SHA-256 去重哈希。

\texttt{AlipayParser} 与 \texttt{WeChatParser} 各自维护一套平台特有的列名映射（如支付宝的「交易对方」→ merchant、微信的「当前状态」→ status），将原生 DataFrame 列映射为 \texttt{ParsedTransaction} 统一结构。Strategy 模式使平台解析器可独立扩展——新增平台只需添加解析器并在 \texttt{ParserRegistry.\_ordered\_parsers()} 中注册。Adapter 模式体现在 \texttt{StatementReader} 类——将 pandas 的复杂 API（多编码、多格式、多表头位置）适配为统一的 \texttt{read(path)} 接口。Registry/Factory 模式通过 \texttt{ParserRegistry} 实现解析器的自动选择与调度。

\subsection{报表构建器}

报表生成由 \texttt{ReportBuilder}（\texttt{services/reports.py:16}）单一类实现，采用 Builder 模式将复杂 PDF 构建过程拆分为有序步骤。

\texttt{build()} 方法编排完整构建序列：\texttt{\_build\_context()} 聚合查询交易数据与分类映射 → \texttt{\_add\_cover()} 渲染深蓝色封面 → \texttt{\_section\_title()} 与 \texttt{\_metric\_row()} 渲染摘要指标卡片 → \texttt{\_simple\_table()} 渲染分类汇总与 Top 商户表格 → 逐分类渲染交易明细页 → 保存 PDF 并写入 \texttt{GeneratedReport} 记录。\texttt{\_resolve\_unicode\_font()} 按优先级搜索 8 个候选路径（项目内置字体、Windows/Linux 系统字体目录），自动检测中文字体。

Builder 模式使每个方法关注单一渲染关注点，扩展新章节只需新增方法并在 \texttt{build()} 中插入调用。\texttt{\_build\_context()} 的数据聚合与渲染逻辑分离，使同一份数据可用于不同渲染阶段。

关键设计决策：\texttt{transactions} 表以 \texttt{(user\_id, dedupe\_hash)} 联合唯一约束阻止重复导入；双分类字段（\texttt{auto\_category\_id} 与 \texttt{final\_category\_id}）使模型建议与人工修正共存，后者非 NULL 时优先；\texttt{needs\_review} 布尔字段标识低置信度或未分类交易，前端按此提取校正队列；\texttt{classification\_results} 只增不改，保留每次分类的完整记录用于追溯；\texttt{classification\_caches} 以 \texttt{(user\_id, provider, text\_hash)} 唯一约束确保缓存按用户与 provider 隔离。

\subsection{家庭组织与报表扩展}

扩展域涵盖 \texttt{organizations}、\texttt{organization\_members}、\texttt{report\_jobs}、\texttt{generated\_reports} 四张表（\texttt{users} 与 \texttt{transactions} 与核心域共享）。

关键设计决策：\texttt{organization\_members.role} 为枚举语义（owner/admin/member），owner 拥有完整管理权限，admin 可管理普通成员，member 仅可查看聚合数据。家庭组织不改变交易归属——聚合查询通过收集 \texttt{organization\_members.user\_id} 列表并以 \texttt{transactions.user\_id IN (...)} 过滤实现，而非新增 \texttt{organization\_id} 外键。\texttt{report\_jobs} 记录生成请求的状态流转（queued → processing → done/failed），\texttt{generated\_reports} 记录输出文件路径。

\section{核心流程设计}

\subsection{账单导入与大模型初分}

用户上传账单文件的完整处理链路包含六个阶段。(1) 前端通过 \texttt{POST /api/imports} 上传文件，后端创建 \texttt{ImportBatch} 与 \texttt{UploadedFile}，前端轮询 \texttt{GET /api/imports} 跟踪批次进度。(2) \texttt{ParserRegistry} 检测平台后，由 \texttt{StatementReader} 读取文件，对应平台解析器将原生列映射为 \texttt{ParsedTransaction}。(3) \texttt{TransactionNormalizer} 做 NFKC 归一化并生成 \texttt{dedupe\_hash}，写入前按唯一约束去重。(4) 每笔交易传入 \texttt{CompositeClassifier.classify()}，按缓存→模型→规则的顺序获取分类结果。外部模型请求进入重试队列由后台线程串行消费，超时则按指数退避策略重试（等待间隔为 $\text{base\_delay} \times 2^{\text{retry\_count}}$，上限 300 秒）。(5) 分类结果同时写入 \texttt{transactions} 表（更新 \texttt{auto\_category\_id/confidence/provider/needs\_review}）和 \texttt{classification\_results} 表（新增不可变历史记录）。(6) 全部交易处理完毕后，\texttt{ImportBatch.status} 更新为 \texttt{done} 或 \texttt{partial\_failed}。

\subsection{家庭组织聚合查询}

家庭组织视图的数据聚合不改变交易归属，在查询层面通过成员身份进行范围扩展。用户进入组织页面后，前端调用 \texttt{GET /api/organizations} 获取当前用户加入的所有组织及角色。查看家庭 Dashboard 或消费人格时，前端传入 \texttt{organization\_id} 参数。后端先校验成员身份（非成员返回 403），再通过 \texttt{get\_member\_user\_ids()} 收集全部成员 \texttt{user\_id} 列表，传入对应的聚合服务。Dashboard 返回家庭总支出/收入/净流入与分类分布，Personality 基于全部成员交易计算家庭整体消费人格画像与财务健康评分，Reports 生成聚合 PDF 报表。
