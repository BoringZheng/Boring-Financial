\chapter{程序开发}

本章阐述系统的程序组织方式、数据库设计、设计模式应用以及核心流程设计。重点说明这些设计如何支撑多平台账单解析、语义分类、人工校正、家庭聚合与报表生成，而不是逐行展开具体代码。

\section{面向对象程序组织}

系统并非全量采用面向对象范式。对于认证、接口编排和简单聚合计算，过程式组织更直接；对于账单解析、分类策略、领域实体和报表生成等存在扩展变化点的部分，则采用面向对象方法控制复杂度。

\subsection{领域实体及其关联关系}

系统使用 ORM 建立领域实体与数据库表之间的映射，采用 Data Mapper 模式将领域概念与持久化细节解耦。实体对象主要表达用户、账单、交易、分类、组织和报表之间的关系，查询与事务处理则由服务层统一承担。

对于创建时间、更新时间等跨实体通用属性，系统采用 Mixin 方式复用公共字段，避免在多个实体中重复维护相同定义。该设计降低了后续调整审计字段时的维护成本。

实体关联的核心拓扑以用户为中心展开：用户拥有导入任务、交易记录、自定义分类和报表；导入批次关联原始上传文件与解析后的交易；交易同时保留系统建议分类和用户最终确认分类，以支持“AI 初分 + 人工校正”的业务闭环；家庭组织通过成员关系连接多个用户，在不改变个人账本归属的前提下实现聚合分析。

交易实体的关键设计是去重、分类追溯和最终口径分离。系统通过交易特征生成稳定指纹来识别重复导入；建议分类与最终分类分开保存，使模型判断和人工修正可以并存；分类历史以追加方式记录，便于后续分析分类策略变化。

\subsection{分类器策略}

分类子系统围绕策略、责任链与外观三种模式组织，用于在规则分类、缓存分类、外部大模型和本地模型之间建立可替换、可降级的分类链路。

外观对象对外提供统一分类入口，内部按“缓存优先、模型判断、规则兜底”的顺序组织责任链。模型服务不可用或超时时，系统不会阻塞整批导入，而是将交易转入后续重试流程；规则分类作为最低保障，确保系统在外部依赖异常时仍能给出基础结果。外部模型与本地模型遵循同一输出约定，因此后续更换模型供应商时不需要改动上层业务流程。

Strategy 模式使不同分类策略可以独立演进；Chain of Responsibility 提供清晰的降级路径；Facade 模式隐藏缓存、重试和结果记录等内部复杂性，使导入流程只需关心“获得分类建议”这一业务结果。

\subsection{账单解析器}

解析子系统负责将微信/支付宝异构账单文件转换为统一交易结构，采用策略、适配器与注册表三种模式。

解析子系统先识别账单来源，再选择对应解析策略，将不同平台的列名、编码和表头差异统一转换为系统内部交易格式。读取器负责屏蔽文件编码和表格格式差异，解析器负责平台语义映射，规范化环节负责生成稳定的交易特征。

支付宝与微信账单的差异被封装在各自解析策略中，上层导入流程只处理统一交易结果。Strategy 模式支持新增平台时局部扩展；Adapter 模式把底层文件读取复杂性收敛为统一读取能力；Registry/Factory 模式负责解析器选择，避免在业务流程中堆积平台判断逻辑。

\subsection{报表构建器}

报表生成采用 Builder 模式，将复杂 PDF 构建过程拆分为封面、摘要指标、分类汇总、商户排行和交易明细等有序步骤。

构建过程先准备统计上下文，再按固定顺序渲染各章节，最后保存报表并记录生成结果。数据聚合与版面渲染分离，使同一份统计数据可以服务于不同报表页面，也便于后续加入新的分析章节。

Builder 模式使每个构建步骤关注单一报表片段，新增章节时只需扩展构建序列，不会影响导入、分类和看板等其他业务模块。

\section{数据库设计}

系统数据库共 12 张表，按业务域分两组展示，分别对应核心账单分类闭环和家庭组织、报表等扩展能力。

\subsection{核心账单与分类}

核心域涵盖用户、分类、分类规则、导入批次、上传文件、交易、分类结果和分类缓存八类数据对象。

关键设计决策包括：按用户维度识别重复交易，避免同一账单被反复导入；同时保存建议分类和最终分类，保证人工校正优先于自动判断；低置信度交易被纳入校正队列；分类历史采用追加记录，支持追溯模型表现；分类缓存按用户和供应商隔离，避免跨用户数据混淆。

\subsection{家庭组织与报表扩展}

扩展域涵盖家庭组织、组织成员、报表任务和已生成报表四类数据对象，并复用核心域中的用户与交易数据。

关键设计决策是家庭组织不改变个人交易归属，而是在查询时按成员范围聚合数据。家庭所有者、管理员和普通成员拥有不同操作权限；报表任务独立记录生成状态，已生成报表独立记录输出结果，便于用户重复下载和运维人员排查失败任务。

\section{核心流程设计}

\subsection{账单导入与大模型初分}

用户上传账单文件的完整处理链路包含六个阶段。(1) 用户提交账单文件后，系统创建导入任务并向页面反馈处理进度。(2) 系统识别账单平台，选择对应解析策略，将不同格式转换为统一交易结构。(3) 交易进入规范化与去重环节，重复记录被跳过，新交易进入分类流程。(4) 分类链路按缓存、模型、规则的顺序生成分类建议，外部模型异常时转入重试机制。(5) 系统保存分类建议、置信度和理由，同时记录分类历史，便于后续追溯。(6) 导入任务结束后，页面展示成功、失败和待复核交易数量，引导用户进入校正或分析页面。

\subsection{家庭组织聚合查询}

家庭组织视图的数据聚合不改变交易归属，而是在查询层面根据成员身份扩大统计范围。用户进入组织页面后，系统展示其加入的组织、角色和成员信息。查看家庭看板、人格画像或报表时，系统先确认用户属于该组织，再汇总组织成员的交易数据。看板返回家庭收入、支出、净流入和分类分布，人格分析基于成员交易计算家庭整体画像，报表模块生成家庭口径的 PDF 文档。
