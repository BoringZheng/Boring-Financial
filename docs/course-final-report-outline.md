# Boring Financial 最终报告结构大纲

## 使用原则

本大纲按老师给出的提交要点重组最终报告。报告保留“项目概述”和“总结”作为首尾章节，中间按软件工程交付过程展开：可行性与规划、需求分析、用户界面与体验设计、系统设计、程序开发、验收发布、运行维护。

正文采用工业项目口径，项目故事统一为：针对市面上记账软件自动分类模糊不清、难以解释和难以修正的问题，Boring Financial 通过“大模型初分 + 人工校正”完成账单分类，并在此基础上支持个人分析、消费人格、家庭组织聚合和 PDF 报表。

写作约束：

- 不提历史实现或迁移背景。
- 不把外部评审人员作为业务利益相关者。
- 非必要表格尽量用正文说明，只保留能支撑软件工程论证的图表。
- 面向对象部分如实说明：项目不是全系统纯 OO，而是在 ORM 实体、分类策略、解析器、报表构建器和 DTO 中使用面向对象组织方式。
- 家庭组织、消费人格、新版前端和生产环境部署均属于当前项目范围。

## 第 1 章 项目概述

### 内容概要

从个人记账自动分类误判切入。例如，用户充值东南大学饭卡时，商户名称可能显示为“东南大学”，传统关键词分类容易归入“学习”，但真实消费意图更接近“餐饮/校园卡充值”。项目目标是让系统先用大模型理解交易语义，再由用户对低置信度或误判交易进行人工校正。

本章说明项目目标、业务范围和边界。范围内包括注册登录、账单导入、交易解析、大模型初分、人工校正、分类管理、Dashboard、消费人格、家庭组织、PDF 报表和部署；范围外包括支付、转账、清算、银行级风控和商业化运营后台。

## 第 2 章 可行性分析与项目规划

### 内容概要

本章对应“可行性分析与规划”提交要点。写作口径是假设评审者是项目决策者，因此要说明项目是否值得做、能否做成、风险是否可控。

内容包括：

- 业务可行性：自动分类误判影响统计质量，大模型初分与人工校正能提升准确性和可控性。
- 技术可行性：FastAPI、Vue、SQLAlchemy、Docker、Nginx、Redis 和 OpenAI-compatible provider 能支撑轻量生产化原型。
- 进度可行性：按 MVP 闭环推进，先完成核心账单整理，再扩展消费人格、家庭组织和部署。
- 资源可行性：本地开发和低配服务器部署可支持项目运行。
- 开发流程：采用轻量级迭代开发，原因是账单格式、模型分类效果和交互体验都需要在联调中验证。
- 项目计划：用 WBS 说明需求、原型、后端、前端、模型分析、测试发布等交付物。
- 团队协作：说明成员职责、Git 协作、接口文档、模块边界和测试用例如何降低人员变动风险。

### 内容概要

本章对应“需求分析”提交要点，重点回答需求从哪里来、有哪些需求、如何建模。

## 第 6 章 程序开发与面向对象设计

### 内容概要

本章对应“程序开发”提交要点，强调程序如何组织、如何体现面向对象和设计模式。注意不写成代码讲解，而是用代码结构作为工程证据。

内容包括：

- 核心模块：Auth、Imports、Transactions、Classification、Categories、Dashboard、Personality、Organizations、Reports。
- 数据库设计：用户、家庭组织、组织成员、分类、导入批次、上传文件、交易、分类结果、分类缓存、报表任务、生成报表。
- 面向对象边界：系统不是全代码严格 OO，而是“面向对象数据模型 + 策略对象 + 分层服务”。
- OO 体现位置：ORM 实体、分类器策略、账单解析器、报表构建器、Pydantic DTO。
- 关键顺序：账单导入与大模型初分，覆盖上传、解析、标准化、分类、落库和异常重试。
- 设计模式：分层架构、Strategy/Provider、Adapter/Registry、Builder、DTO、RBAC。
